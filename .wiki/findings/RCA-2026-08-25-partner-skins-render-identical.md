# RCA 2026-08-25: seven partner-skin tiles render byte-identical (as a green ring)

- **Date:** 2026-08-25
- **Reporter:** team lead, after Nico reported the game "got visibly worse" following an outside agent's uncommitted hole-skin rework. Hard evidence supplied: 7 of 8 `docs/skins/partner-*.png` share sha256 `c3b8928c...` and show a plain green ring instead of the partner brand colors.
- **Severity:** none in the game (working as designed); low for the docs artifact; medium as a process finding (a failing generator's output was shipped without comment).

## 1. Symptom

As reported: after the skins rework, `docs/skins/partner-huble.png`, `partner-impulse`, `partner-kuno`, `partner-mediajunction`, `partner-newbreed`, `partner-saltedstone` and `partner-sixandflow.png` are byte-identical and render a plain green ring; only `partner-supered.png` differs. Brand colors are still present in the SKINS registry rows.

Precise characterization: the seven tiles are byte-identical to `docs/skins/classic.png` (verified: all share sha256 `c3b8928c9f23...`). They are renders of the Classic Green skin written under partner filenames by the contact-sheet generator.

## 2. Root cause (confidence: confirmed)

This is not a rendering bug and not a harness bug. The seven partner skins were **deliberately withdrawn on 2026-08-17** (commit `6824327`, "feat(skins): gate partner skins on approval, refund the withdrawn seven (v24)") because only Supered has granted permission to show its logo. `resolveAvailableRow()` in `js/skinapproval.js:48` resolves any withdrawn partner id to the free `classic` row, fail closed, by design. The checked-in partner PNGs at HEAD predate that withdrawal (last regenerated by commit `039c714`, 2026-08-07), so nobody had ever re-baked the contact sheet after the gate landed. The outside agent's regeneration during the skins rework was the **first bake since the withdrawal**, and it honestly shows what the game now shows: withdrawn partner id resolves to Classic. The docs artifact caught up with a ten-day-old product decision; the "regression" is the disappearance of stale tiles.

## 3. Causal chain

- **Trigger:** the outside agent re-ran `tools/skinsheet.mjs` as part of the 2026-08-24 skins rework, regenerating every file in `docs/skins/`.
- **Mechanism:** `tools/skinsheet.mjs:71` calls `bakeSkinThumbnails()` (`js/skins.js:2547`), which bakes each row via `makeSkin(row.id)` (`js/skins.js:2591`). `makeSkin` resolves the id through `skinRowFor()` (`js/skins.js:2452`, `js/skins.js:736`), which calls `resolveAvailableRow(SKIN_BY_ID, id, 'classic')`. `isSkinAvailable()` (`js/skinapproval.js:26`) returns false for any `family: 'partner'` row without `approved === true`. Only `partner-supered` carries the flag (`js/skins.js:617`), so the other seven bake the Classic Green builder, producing seven byte-identical PNGs.
- **Root cause:** the 2026-08-17 withdrawal decision (commit `6824327`, `WITHDRAWN_PARTNER_SKIN_IDS` at `js/skinapproval.js`), combined with stale committed PNGs from 2026-08-07 that made the first honest regeneration look like breakage.
- **Contributing factors:**
  - `docs/skins/*.png` were never regenerated when the approval gate landed, so the docs contradicted the shipped behavior for ten days (stub or stale metadata fails exactly like broken content).
  - `tools/skinsheet.mjs` DID catch this: its byte-identical assertion (`tools/skinsheet.mjs:115`) prints `PROBLEM: byte-identical tiles` and exits 1. But it writes the PNGs and index.html BEFORE asserting, so a failing run still leaves regenerated files, and the outside agent shipped them without mentioning the red exit. The skinsheet header comment (`tools/skinsheet.mjs:21`) also claims the classic-fallback hazard "cannot arise from a mis-bound save," which is true but incomplete: it arises from the approval gate, exactly as observed.

## 4. Evidence log

- `sha256sum`: `docs/skins/classic.png` == `docs/skins/partner-huble.png` (`c3b8928c...`); `partner-supered.png` differs (`34a586f3...`).
- At HEAD (`git show HEAD:docs/skins/...`): classic, partner-huble and partner-impulse all DISTINCT, last touched by `039c714` (2026-08-07). The approval gate is `6824327` (2026-08-17). `git merge-base --is-ancestor` confirms the PNG commit predates the gate.
- Live app proof (Playwright against `python -m http.server 8152`, real `VoxelWorld3D` on Singapore, computed state not pixels): `makeSkin(id).row.id` returned `classic` for exactly the seven withdrawn ids and `partner-supered` for Supered. Matches `WITHDRAWN_PARTNER_SKIN_IDS` (`js/skinapproval.js:69`) one for one.
- **Hypothesis (a), game build path broken (logoTex failure or throwing builder): falsified.** `buildPartner` (`js/skins.js:2275`) is untouched by the diff; the live resolution shows the classic substitution happens BEFORE any builder or texture runs, at id resolution.
- **Hypothesis (b), harness screenshots the same skin 7 times or crashes per skin: falsified.** The new `tools/pw/skin-shots.mjs` writes to `tools/pw/_skin-shots/`, not `docs/skins/`, and its skin list contains no partner ids at all; `docs/skins` comes from the pre-existing `tools/skinsheet.mjs`, which renders per row with no stale-state seam (fresh `makeSkin` per row, disposed after).
- **In-game blast radius of the rest of the rework: none found at the error level.** All SKINS rows (including the rewritten Sprocket, Burn Rate, Pipeline, Cold Outreach, Radar, TAM, A/B, Attribution, Compounding, Shredder, Closer, Eyeballs, Throat, Chomper builders) were hot-swapped onto a live world and driven 120 frames each with bite events: zero exceptions, zero page errors. The shop cannot offer withdrawn rows (`js/upgrades.js:160` filters on `isSkinAvailable`), so no player-visible partner damage exists.
- `.wiki/modules/render.md` addition audited: it documents the rework pattern and the harness; no past-tense "verified" claims that the code does not back were found.

## 5. Blast radius and siblings

- Game: unaffected. Withdrawn skins are unreachable in the shop and resolve to Classic anywhere an old save or a multiplayer peer supplies their id, which is the gate's designed purpose.
- Docs: `docs/skins/index.html` now shows seven Classic tiles under partner names and captions with the brand swatches, which is confusing to a reader who does not know about the withdrawal.
- Sibling check: `indicatorRowFor()` (`js/skins.js:745`) shares the same resolution rule; `ind-supered` is approved, so no indicator tile is affected. No other consumer of `resolveAvailableRow` exists.

## 6b. Ride-along finding (2026-08-25): partner logo paths are document-relative and 404 under `tools/`

Surfaced by the scene-viewer controls work: every scene loaded via `tools/scene-view.html` logs 7 404s because the `logoTex` paths in the SKINS registry (`js/skins.js:633` etc.) are relative (`assets/skins/partners/...`), so a page living under `tools/` requests `/tools/assets/...`. **Pre-existing at HEAD** (`git grep` confirms the same 7 relative paths in the committed file), identical on every scene, unrelated to the rework and to the camera change — cosmetic in the dev viewer (texture load fails, builders fall back), invisible in the root-served game.

Fix: resolve the paths against the module rather than the document — e.g. `new URL('../assets/skins/partners/...', import.meta.url)` at the point of texture load, or a single `ASSET_BASE` derived from `import.meta.url`. Do NOT hardcode a leading `/` (breaks subpath deploys). The fix touches `js/skins.js`, which is frozen pending Nico's keep-vs-revert call on the rework — apply it as step 5 of path (i), or as a follow-up commit immediately after path (ii)'s revert.

## 7. Prevention

- Regenerate derived artifacts in the same commit as the decision that invalidates them: the approval gate commit should have re-baked `docs/skins/`. A stale derived artifact turns the next honest regeneration into a false alarm.
- A generator's assertions must run before its writes (or writes must be transactional), and a red generator exit must be reported by whoever ran it, never shipped as if green. The assertion here worked; the reporting did not.
