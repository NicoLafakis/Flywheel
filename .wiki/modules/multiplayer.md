# Multiplayer System

`js/multiplayer/` implements low-latency, zero-storage, authoritative multiplayer over Supabase Realtime Broadcast.

## Architecture

- **Transport (`js/multiplayer/channel.js`)**: Ephemeral WebSocket broadcast layer. Messages are never written to disk or database. Includes outbound queueing until `SUBSCRIBED`.
- **Wire Protocol (`js/multiplayer/protocol.js`)**: Standardized messages (`JOIN_REQUEST`, `ROOM_STATE`, `START_VOTE`, `GAME_START`, `INPUT_TICK`, `STATE_SYNC`, `PVP_KILL`, `GAME_OVER`).
- **Lobby (`js/multiplayer/lobby.js`)**: Room creation, 5-character codes, invite links (`/?room=CODE`), ephemeral chat, and the 3-second countdown that precedes a match. See **Start control** below for what is allowed to begin that countdown.
- **Selectable Cities (`MULTIPLAYER_SCENES` in `js/multiplayer/config.js`)**: exactly three — `gallery` (The Lab), `manhattan` (Lower Manhattan), `brooklyn` — with their chip copy alongside them in `MULTIPLAYER_SCENE_META`, so adding a fourth city is one edit. The host's CHOOSE METROPOLIS chips are built by mapping that list (`ui.js`), the invite link carries only a room code (never a scene), and a peer takes the scene from the host's `ROOM_STATE`; there is no other way a scene name enters a match. **None of the three declares `sceneMovers`** — `js/voxelscene-chicago.js` is the only scene in the game that does — so `sim.moverSim` is `null` in every match that can be started, `_stepMovers()` returns on its first line, and `VoxelWorld3D._buildMovers()` builds nothing. The open question in `architecture.md` about `host.js`/`peer.js` never referencing `objectIdSpace` or `sceneMovers` is therefore moot for now rather than a live defect: there is no mover in a multiplayer match to consume, desync, or attribute. It stops being moot the moment a mover-bearing city (Chicago) joins the list — riding pose reads `sim.time`, an independent per-client accumulator that `applyClockAuthority()` does NOT reconcile, and `_consumeMoverUnit()` is decided locally on each client with nothing on the wire to arbitrate it, so a train would have to become host-published state in the same pass.
- **Start control (lobby countdown entry points)**: a full room does **not** start itself. `handleJoinRequest` used to call `startCountdown()` the moment `isFull` went true, so the match began the instant the last player finished loading — nobody had picked a skin, nobody had read the chat, and the host had no say. There are now exactly two ways into a countdown:
  1. **The host's button** (`#mp-force-start`, "START NOW (n/capacity)"). Available at any seated count `>= MIN_PLAYERS` (2). This is the normal path and the only one in a 2-player room.
  2. **A unanimous vote of the seated non-hosts** (`START_VOTE`). This exists for ONE situation — the host is seated but has stopped acting — and is deliberately hard to reach:
     - **Locked until the host has been idle `HOST_IDLE_VOTE_UNLOCK_MS` (45 s).** Before that the vote UI is *absent*, not greyed: nothing hints that hurrying the host is available. Idle time never accumulates across activity — each host action restarts the window from zero, so a host who does something every 30 s is never votable past however long the lobby has been open.
     - **Needs `MIN_PLAYERS_FOR_START_VOTE` (3) seated players.** With two, the non-host side of the room is one person, so "unanimous among non-hosts" would just be a second start button. Below three you wait for the host. That seated-count check is the *only* expression of the rule — an earlier second guard on `startVoteRequired` said the same thing a different way and made the constant untestable.
     - **Unanimous among non-hosts.** `startVoteRequired` is every seated non-host; the host is never counted and its own `START_VOTE` is discarded (`voter.isHost`).
     - **Any roster change or host activity wipes the tally and restarts the idle clock** (`_resetStartControl`). Applied at each of the sites that mutate `players` — `handleJoinRequest` and `handlePlayerLeave` on the host, the `ROOM_STATE` handler on a peer — so no reachable roster change can leave a stale tally behind. Two of three votes plus a departure must never read as unanimous among the two who remain.
- **Start control is host-authoritative.** `START_VOTE` is deliberately **not** in `HOST_ONLY_TYPES` — a client is its only honest sender — but the *consequence* stays host-only: a unanimous tally makes the **host** call `startCountdown()`, and `COUNTDOWN_START`/`GAME_START` remain host-only, so a peer that reaches unanimity first (or forges a countdown outright) changes nothing. The vote asks for a start; it never performs one. If the host is genuinely gone rather than idle, `_handleHostDeparture()` tears the room down instead. Votes are bound to a player by the transport's `senderId` stamp, never by the `slot` in the body, for the same reason `PLAYER_LEAVE` is — a body-supplied slot would let one client vote on another's behalf.
- **The gate is host-declared, not independently derived.** On the host, `startVoteAvailable` is **computed** from `hostIdleMs` and never cached — a stored flag would survive a roster change or a returning host and hand the room a start it never earned. On a peer it is simply whatever the host last published in `ROOM_STATE.startVoteOpen`. Peers deliberately do **not** run their own idle clocks: a peer cannot observe a silent host, only its traffic, so a private clock keeps counting through everything the host does that never reaches the wire and opens the vote on a host who was demonstrably active (a host acting at 30 s had every peer unlock at 45 s regardless). The host publishes both transitions — a missed *close* would leave a live vote button on every other screen after the host came back.
- **Ordering rule**: `ROOM_STATE` carries the gate's state, so any roster change must `_resetStartControl()` **before** `_broadcastRoomState()`, or peers adopt a stale `startVoteOpen: true` from the very message announcing the change. The host also skips the vote reset when it hears its own `ROOM_STATE` back over the loopback — resetting there would cancel the announcement it just made — which is why `handleJoinRequest` and `handlePlayerLeave` reset directly instead.
- **Idle watch lifecycle**: `_syncIdleWatch()` arms the 1 Hz gate poll only on the **host**, and only while a vote could become possible (3+ seated, no countdown, host present). Peers and 2-player rooms carry no timer at all, and a live match none either. Starting a countdown also restarts the idle clock (`startCountdown`, and the peer's `COUNTDOWN_START` branch), so a countdown cancelled by a departure does not land back in an already-expired idle window with the vote instantly open.
- **Vote feedback in chat**: `_appendSystemChat()` is local-only and is never broadcast (a system message carries `slot: -1`, which `validateMessage` rejects, so it *cannot* go on the wire). Every screen therefore narrates the vote from the broadcast events it observes for itself — the unlock, each vote landing as `n/m`, and the pass. `_announceVoteGate()` holds the single wording for open/closed, reached by the host from its idle poll and by a peer from the `ROOM_STATE` it adopts, so both screens say the same thing at the same moment.
- **Host Session (`js/multiplayer/host.js`)**: Authoritative physics simulation, input collection across slots, and state broadcasting at 60 Hz.
- **Peer Session (`js/multiplayer/peer.js`)**: Client-side prediction, input transmission, state smoothing.
- **Multi-Hole Presentation Alignment**:
  - `VoxelSandboxSim.localSlot`: Identifies which slot the local client controls (`0` for Host, `mySlot` for Peer).
  - `sim.localHole`: Accessor used by camera, audio listener, controls, and HUD.
  - `VoxelWorld3D`: Renders local player's equipped skin on `sim.localHole`, and dynamically renders colored rival rings for all connected slots $0..N-1$ excluding `localSlot`.
- **PvP Interactions**: Pairwise hole collision swallowing ($r_\text{large} > r_\text{small} \times 1.05$), +50% mass steal bounty, 10s perimeter respawn with fullscreen countdown overlay, and real-time takedown announcements.
- **Host-Authoritative Match Clock (T-635)**: `STATE_SYNC.clockTicks` carries the host's `sim.clockTicks`, and a peer's sim is built with `clockFollower: true`. The peer keeps counting locally between syncs so the countdown stays smooth, then reconciles toward host truth in `VoxelSandboxSim._clockAdvanceTicks()`: a fraction of the error per step (`CLOCK_AUTHORITY_CATCHUP_RATE`, capped by `CLOCK_AUTHORITY_MAX_CATCHUP_TICKS`), snapping outright past `CLOCK_AUTHORITY_SNAP_TICKS` (2 s). Corrections are **forward-only** — a peer that is ahead HOLDS rather than rewinding, so the HUD countdown is monotonic. A follower never latches `timedOut`/`over` on its own clock; `GAME_OVER` from the host remains the only ending, with the host-silence watchdog as the safety net. Before this, every client counted its own `step()` calls: a two-browser match on Lower Manhattan ended with the host at 0.0 s and the peer's HUD still reading 0:38.
- **Shared Coin Pool (T-636)**: `STATE_SYNC.coinsCollected` carries the host's count of coins taken by *anyone*; a peer applies it through `sim.applyCoinAuthority()`, which is monotonic so a stale sync can never put coins back on the map. `sim.coinsRemaining` returns host truth on a peer and local truth on a host or solo run, and the match HUD renders it as `🪙 n LEFT` — one finite pool draining, identical on every screen. Solo play keeps the personal `🪙 collected/total` tally unchanged; the split lives in the pure `formatCoinReadout()` in `js/ui/hud.js`, gated on `sim.isMultiplayer`.
- **Per-Player Coin Isolation & Banking**: Unchanged by the shared readout above — each hole still tracks its own `coinsCollected` and `coins`. Coin pick-up SFX, toasts, and combo pulses fire exclusively for `sim.localHole` while rival pick-ups render silent golden sparkles in 3D. Per-hole coins are synced in `STATE_SYNC.holes[]`, ranked on the victory podium (`COINS EARNED 🪙 +N (M found)`), and deposited into `save.coins` on match conclusion.
- **Podium Music**: both game-over handlers in `js/main.js` (host and peer) call `audio.setMusicCue('victory')` before `showMultiplayerPodium()`. `victory` is registered in `MUSIC_CUES` as an alias onto `post-game.mp3` — the podium is a post-game screen, so it shares the results track rather than shipping a second copy. It was **unregistered** until 2026-08-16, which made `MusicDirector.request()` warn `music: unknown cue "victory"` and play nothing: the end-of-match screen was silent in every match. `tools/music-cue.test.mjs` (in `validateMultiplayer()`) now fails the build on any caller/registry mismatch of that shape.
- **Free Basic Color Skins**: 7 baseline color skins (`baseline-cyan`, `baseline-crimson`, `baseline-amber`, `baseline-emerald`, `baseline-purple`, `baseline-orange`, `baseline-magenta`) costing 0 coins, providing distinct colors across single player and multiplayer.
